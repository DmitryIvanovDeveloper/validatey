# План реализации: Compliance + Analysis-Ready Data

Документ связывает эпики **Compliance by Default** (Epic 10) и **Analysis-Ready Data** (Epic 11) с техническими шагами и порядком внедрения в рамках MVP фаз 1–3.

---

## Общие принципы

1. **Не ломать текущий цикл валидации:** согласие и шаблоны встраиваются в существующие потоки (мастер, опрос, отчёт).
2. **Backend first для compliance:** хранение согласий, разделение PII/ответов — сначала схема и API, потом UI.
3. **Шаблоны как конфиг:** структура шаблонов (Problem/Feature/Value Prop) — данные (JSON/конфиг), а не хардкод в коде.
4. **Поэтапный rollout:** Фаза 1 — минимум для «GDPR-ready» и «3 шаблона»; Фаза 2–3 — расширенный compliance и экспорт.

---

## MVP Фаза 1 (месяц 1)

**Цель:** 3 структурированных шаблона + базовый GDPR (согласие + прозрачность) + простой dashboard.

### 1.1 Шаблоны исследований (US-D.1)

| Задача | Слой | Описание |
|--------|------|----------|
| Зафиксировать 3 шаблона в коде/конфиге | Backend / Shared | Определить JSON-структуру сценариев для Problem Validation, Feature Validation, Value Prop Test (вопросы + типы полей). Сейчас шаблоны частично есть (GetScenarioTemplatesUseCase, InMemoryScenarioTemplateRepository) — расширить до полных сценариев с подсказками метрик. |
| Шаг «Сценарий» в мастере | Frontend | В CreateProjectWizard на шаге сценария: при выборе шаблона подставлять готовые вопросы (редактируемые). Связь с US-1.2. |
| Валидация структуры при сохранении | Backend | При сохранении сценария опционально проверять соответствие выбранному типу шаблона (для будущего US-D.3). |

**Результат:** PM выбирает тип исследования и получает готовый набор вопросов; ответы уже пригодны для расчёта метрик по шаблону.

### 1.2 Согласие и прозрачность (US-C.1, US-C.2)

| Задача | Слой | Описание |
|--------|------|----------|
| Модель данных согласия | Backend | Таблица `consents` или `consent_records`: project_id, invitation_id, consent_text (или id ссылка на текст), accepted_at, ip (опционально), user_agent (опционально). Миграция. |
| Текст согласия в проекте | Backend | В проекте или сценарии поле `consent_text` (или отдельная сущность ConsentTemplate). API: сохранить/получить текст согласия для проекта. |
| Экран согласия перед опросом | Frontend | На `/survey/:token` перед первым вопросом: экран с текстом согласия, чекбокс «Я согласен», кнопка «Продолжить». Блокировать переход к вопросам без принятия. |
| Сохранение факта согласия | Backend | При «Продолжить» вызвать API записи согласия (invitation_id, consent_text_id, timestamp), затем разрешить доступ к вопросам. |
| Краткая информация об использовании данных | Frontend | На экране согласия добавить блок «Как мы используем данные» (цель, доступ, срок, права) — конфигурируемый текст или шаблон. |

**Результат:** Каждый опрос начинается с явного согласия; респондент видит использование данных; факт согласия хранится для аудита.

### 1.3 Dashboard и метрики по шаблонам

| Задача | Слой | Описание |
|--------|------|----------|
| Расчёт метрик по типу шаблона | Backend | В report/calculate-metrics: если проект привязан к шаблону Problem/Feature/Value Prop, считать соответствующие метрики (средняя острота, % понявших фичу, WTP и т.д.) и выводить в отчёт. |
| Progress/Report UI | Frontend | Убедиться, что на Progress и Report отображаются метрики, релевантные выбранному шаблону (уже частично есть — донастроить под 3 шаблона). |

**Результат:** Простой dashboard с метриками, соответствующими типу исследования.

**Критерии завершения Фазы 1:**
- В мастере доступны 3 шаблона с готовыми вопросами.
- Опрос не начинается без принятия согласия; согласия пишутся в БД.
- На экране согласия есть информация об использовании данных.
- Отчёт/Progress показывают базовые метрики по шаблону.

## MVP Фаза 2 (месяц 2–3)

**Цель:** AI-вопросы как опция, расширенная аналитика, предупреждения по структуре, уведомления по запросам удаления, audit log.

### 2.1 Предупреждение о непригодности вопросов (US-D.3)

| Задача | Слой | Описание |
|--------|------|----------|
| Правила валидации по типу шаблона | Backend | Определить для каждого шаблона обязательные типы вопросов (например, для Problem — минимум одна scale). |
| API или use case проверки сценария | Backend | При сохранении сценария (или по отдельному запросу) возвращать предупреждения: «для расчёта метрик по Problem Validation рекомендуется шкала остроты». |
| UI предупреждения | Frontend | В мастере при сохранении сценария или при переходе к шагу «Приглашения» показывать предупреждение, если структура не соответствует шаблону. Не блокировать сохранение. |

### 2.2 Экспорт сырых данных (US-D.2)

| Задача | Слой | Описание |
|--------|------|----------|
| API экспорта ответов | Backend | GET `/projects/:id/responses/export` (или аналог): возврат JSON/CSV с question_id, type, value, invitation_id (анонимный), timestamp. Права: только владелец/роль. |
| JSON Schema для ответов | Backend | Генерация или документирование схемы ответов по типу сценария (для аналитиков). |
| Кнопка экспорта в UI | Frontend | На странице Progress или Report кнопка «Export raw data» (JSON/CSV). |

### 2.3 Уведомления о запросах на удаление (US-C.3)

| Задача | Слой | Описание |
|--------|------|----------|
| Модель запроса на удаление | Backend | Таблица `deletion_requests`: email или identifier, project_id, status, requested_at, completed_at, requested_by. |
| API создания запроса | Backend | Публичный или внутренний endpoint для создания запроса (форма на сайте, webhook). |
| Уведомление админу/PM | Backend | При создании запроса — отправка email или in-app уведомления владельцу проекта / админу. |
| Список запросов и статусы | Frontend | Страница проекта или отдельная «Compliance»: список запросов на удаление со статусом; кнопка «Выполнить» (переход к one-click deletion в Фазе 3). |

### 2.4 Audit log (базовый)

| Задача | Слой | Описание |
|--------|------|----------|
| Логирование критичных действий | Backend | Запись в таблицу audit_log: user_id, action (e.g. project_view, report_export, consent_export), resource_type, resource_id, timestamp, ip. |
| Доступ к логам | Backend | API для чтения логов (только админ или владелец проекта) — опционально в Фазе 2, минимум запись. |

**Критерии завершения Фазы 2:**
- При сохранении сценария показывается предупреждение, если вопросы не подходят под шаблон.
- Доступен экспорт сырых ответов в JSON/CSV.
- Запросы на удаление можно создавать и видеть в интерфейсе; уведомления уходят PM/админу.
- Критичные действия пишутся в audit log.

## MVP Фаза 3 (месяц 4–6)

**Цель:** Панели респондентов, выполнение удаления (one-click), экспорт согласий, API для BI.

### 3.1 One-click deletion (GDPR/DSAR)

| Задача | Слой | Описание |
|--------|------|----------|
| Use case удаления данных респондента | Backend | По идентификатору (email/invitation_id): удалить или анонимизировать PII, при необходимости анонимизировать ответы (или удалить по политике). Обновить статус deletion_request. |
| Кнопка «Delete Respondent Data» | Frontend | В карточке запроса на удаление или в списке приглашений: кнопка выполнения удаления с подтверждением. |
| Срок выполнения | Backend / Process | Документировать SLA (например, 24 ч); уведомление заявителю после выполнения (опционально). |

### 3.2 Экспорт согласий для аудита (US-C.4)

| Задача | Слой | Описание |
|--------|------|----------|
| API экспорта согласий | Backend | GET `/projects/:id/consents/export` → CSV/JSON: invitation_id, email (или хэш), timestamp, consent_text_id. |
| Кнопка в UI | Frontend | В настройках проекта или разделе Compliance: «Export consents». |

### 3.3 Панели респондентов (US-3.5)

| Задача | Слой | Описание |
|--------|------|----------|
| Интеграция с панелью | Backend / External | Выбор провайдера (Respondent, Prolific или свой пул); API или ручная загрузка целевых респондентов; отправка ссылок на опрос. |
| UI выбора «Купить аудиторию» | Frontend | В мастере на шаге «Как найдём респондентов» опция «Панель»; экран выбора сегмента, бюджета, запуска кампании. |

### 3.4 API для BI

| Задача | Слой | Описание |
|--------|------|----------|
| API для экспорта в BI | Backend | Стабильный формат (JSON Schema), аутентификация по API key или OAuth; rate limit. Документация для аналитиков. |

### 3.5 Auto-anonymization (опционально)

| Задача | Слой | Описание |
|--------|------|----------|
| Фоновая задача | Backend | По расписанию (например, раз в день): находить записи старше N дней, анонимизировать PII или ответы согласно политике проекта. |

**Критерии завершения Фазы 3:**
- Запрос на удаление можно выполнить одним действием; данные респондента удаляются/анонимизируются.
- Согласия экспортируются одним кликом.
- Респондентов можно привлекать через панель (хотя бы один канал).
- Доступен API экспорта для BI и документация.

## Зависимости и порядок

```
Фаза 1:
  Шаблоны (1.1) ──► можно делать параллельно с 1.2
  Согласие (1.2) ──► миграция consents → API → экран в survey → сохранение
  Dashboard (1.3) ──► после 1.1 (метрики по шаблону)

Фаза 2:
  US-D.3 (2.1) ──► после 1.1 (шаблоны зафиксированы)
  US-D.2 (2.2) ──► независимо
  US-C.3 (2.3) ──► модель deletion_requests → API → уведомления → UI
  Audit log (2.4) ──► можно внедрять постепенно в любые use cases

Фаза 3:
  One-click deletion (3.1) ──► после 2.3 (запросы уже есть)
  US-C.4 (3.2) ──► после 1.2 (согласия уже хранятся)
  US-3.5 (3.3), API BI (3.4), Auto-anonymization (3.5) ──► по приоритету продукта
```

## Риски и митигация

| Риск | Митигация |
|------|-----------|
| Юридические формулировки согласий различаются по странам | Шаблоны согласий вынести в конфиг/админку; возможность кастомизации текста под юрисдикцию. |
| Перегрузка экрана опроса (согласие + много текста) | Краткий блок «Как используем данные» + ссылка на полную политику; один экран «Согласие + Продолжить». |
| Запросы на удаление вручную обрабатываются долго | Чёткий SLA (24–72 ч), напоминания в UI, метрика «время до выполнения». |
| Экспорт сырых данных увеличивает нагрузку | Пагинация, фоновые задачи для больших объёмов, rate limit на API. |
